## 5. Local file system edge cases

### 5.1 Lossy watcher events and rescans

Watcher events are hints about where to look, never facts about what changed. `inotify` is not recursive, needs a watch per directory, is limited by `max_user_watches`, and drops events with `IN_Q_OVERFLOW` when its queue fills ([inotify(7)](references.md#ref-inotify)). FSEvents coalesces events and asks the client to rescan a subtree (`kFSEventStreamEventFlagMustScanSubDirs`), and reports dropped events with `KernelDropped` or `UserDropped` ([Apple FSEvents guide](references.md#ref-fsevents)). So, as `core/fs` already does, watchers only choose which subtrees to rescan, and a rescan compares the disk with the last snapshot and reports created, modified, renamed and removed entries with their file identities. A lost event becomes a wider rescan; it never becomes an assumption. This is what B&P call a safe update detector: it may report more than changed, never less.

Patterns the fs layer turns into the right observation:

- **Rename over an existing file** (an editor's atomic save: write a temporary file, then rename it over the original): reported as a modification of the original file, so the node keeps its ID and version history.
- **Delete and re-create at the same path** within the debounce window: also a modification when the kind is the same.
- **[changed] Swap or rotation through a third name** (`mv a tmp; mv b a; mv tmp b`), of files or folders: an entry whose identity was at another path before the rescan, while the identity its path held is at another path after it, is reported as renames, so each node keeps its ID and version history. The planner sends the renames through a pending name (§2.6).
- **Ignored names** (`.koidrive/`, platform files such as `.DS_Store` or `Thumbs.db` per a fixed list, and paths matched by `.koiignore`, §5.10): invisible to the engine, but they still occupy names on disk, so an effect that needs that name fails its check and is reported as a problem. **[changed]** The platform files do not keep a folder from being removed (§5.2).

### 5.2 Applying effects without losing user bytes

**[changed]** This section replaces the exchange-and-swap-back procedure of d37ee0d, which could lose a user write in a crash and fell back to a plain replacing `rename` on some file systems (review B1, B2).

The driver gives three separate guarantees, and claims nothing beyond them:

- **Atomic names.** Every change to a name in the sync root is a single `rename` or `mkdir` that never replaces an existing entry. A replacement is two such changes (the old file leaves for quarantine, then the new one arrives), so between steps 3 and 4 below the target name is briefly absent; another process sees the old file, no file, or the new file, never a partial one.
- **No lost user bytes.** An effect never unlinks or overwrites an entry. Anything it displaces is renamed into `.koidrive/quarantine/`, compared with what the engine expected, and then either moved to the local trash (when it is exactly the synced content, which the server also holds) or returned to the user. This holds across process crashes, for the writers the contract below supports.
- **Durability.** Process-crash recovery is guaranteed by the effect record and the ordering below. Survival of a power loss depends on the file system and the drive honoring flushes; it is not claimed beyond that, and only native tests can check it (§7.4).

**Required primitives.** A rename that fails instead of replacing: `renameat2(RENAME_NOREPLACE)` on Linux ([rename(2)](references.md#ref-rename)) or `renamex_np(RENAME_EXCL)` on macOS ([renamex_np(2)](references.md#ref-renamex)). The driver probes for it in `.koidrive/` when a space is linked and on every start. A file system without it (some network and FUSE file systems) is refused: the space is not synced and a problem is reported. There is no check-then-`rename` fallback, because a plain `rename` replaces its target, and backing the target up first only moves the window ([rename(2)](references.md#ref-rename)). Exchange (`RENAME_EXCHANGE`, `RENAME_SWAP`) is no longer used.

**Path resolution.** The driver holds a descriptor for the sync root and resolves every path from it, one component at a time, without following links: on Linux with `openat2` and `RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS` ([openat2(2)](references.md#ref-openat2)), elsewhere with `openat(O_NOFOLLOW | O_DIRECTORY)` per component. Each directory's `(dev, ino)` is compared with L before it is used, and every rename is a `renameat` between directory descriptors. A parent replaced by a symbolic link or by another directory after the scan fails the identity check instead of redirecting the effect. A descriptor does not follow its directory being moved, though: if the user moves a parent out of the root after resolution, a `renameat` on the held descriptor acts outside the root. The driver therefore resolves the path again from the root immediately before each rename and compares the result with the held descriptor's identity; a mismatch fails the effect. A move in the short window between that check and the rename stays possible; it can only move the entry within the same file system, never destroy it.

**The effect record.** Before an effect that creates, replaces, moves or removes anything is handed to the driver, the engine persists its record in the same store transaction that emits it: `effect_id`, kind, the target as (parent directory identity, name), the expected state of the entry being displaced (identity, size, mtime, manifest digest), the new content for a write, and two private paths derived from `effect_id`: `.koidrive/staging/<effect_id>` and `.koidrive/quarantine/<effect_id>`. Staging only ever holds bytes downloaded from the server and verified against their hashes; the driver never moves a user's file into staging. Quarantine holds displaced entries and is never swept.

**Replacing a file** (`WriteFile` with `replaces`):

1. Download chunks into the content-addressed chunk cache, verifying each chunk's SHA-256 (spec §10). Assemble the file at the staging path, verify the manifest digest, set the executable bit, and flush it.
2. Compare the target with the expected state. On a mismatch, stop: `EffectFailed`, nothing was displaced.
3. Rename the target to the quarantine path (no-replace). From here on, whatever the user had at the target, even if they wrote it after step 2, is in quarantine and intact.
4. Compare the quarantined entry with the expected state, including its content digest.
   - Match: rename staging to the target (no-replace). If the target name has been taken in the meantime, leave the new entry alone and delete the staging file; the quarantined file is synced content and still goes through step 5, after which the effect is reported as `EffectFailed`.
   - Mismatch: the user wrote between steps 2 and 3. Rename the quarantined entry back to the target (no-replace) and report `EffectFailed`. If the target name has been taken again, the quarantined entry stays and is reported as a **recovered** local file (below).
5. Move the quarantined entry, which now equals the synced content, to `.koidrive/trash/`. Report `EffectDone`.

**Removing** (`RemoveFile`, `RemoveDir`) is steps 2 to 5 without staging: quarantine, compare, then trash or put back. A directory must be empty once quarantined; an entry created in it in the meantime makes it a mismatch. **[changed]** Platform files are the exception (GUN-305): a quarantined directory that holds nothing but regular files with the exact names of the fixed list (`.DS_Store`, `Thumbs.db`, `desktop.ini`, `Icon\r`) matches, and the driver deletes those files before it moves the directory to the trash. Scans leave these files out, so no effect removes them first. The Finder keeps a folder's view data in a `.DS_Store` file inside it; Apple documents these files for network shares ([Apple Support](references.md#ref-ds-store)), and that the Finder also writes them on local volumes is common knowledge with no Apple page found for it (unverified). Without the exception a folder deleted on another device would stay on a Mac as a folder that looks empty. The files are deleted rather than trashed with the folder because the trash deletes a folder only while it is empty and recovers it otherwise, which would bring the folder back when it expires. Syncthing has the same case: an ignored file can block the removal of a directory, and its `(?d)` pattern prefix, meant for files the operating system generates, allows removing such a file then ([Syncthing documentation](references.md#ref-syncthing-ignore)). Any other entry keeps the folder, including a file that a `.koiignore` rule or the device-local list excludes: the effect fails, everything is put back, and the folder is reported as a problem. **[changed]** The failure names those entries, and the driver does not plan the removal again after a wait, since only the person can change what the folder holds: the status names the entries until the effect planned for the folder changes or the folder restarts (GUN-398). A wait for another failed effect leaves it blocked, and a folder to remove that holds it waits behind it without keeping the folder from being up to date. **Creating** (`CreateDir`, `WriteFile` without `replaces`) is a no-replace `mkdir` or rename from staging. **Moving** is one no-replace rename after the source's identity check. A rename never destroys content, so a source the user changed after the check is moved with its new content, and the next rescan reports that content as a local edit.

A **recovered** file is a quarantined entry that cannot go back to its name. The driver renames it into the same directory as `<stem> (recovered <YYYY-MM-DD>)<ext>` (no-replace, with a counter on collision) and reports it as an observation, so it becomes an ordinary new local file and is uploaded. If that directory no longer resolves to the one the effect expected, the recovered file goes to the sync root instead.

**Supported writers.** **[changed]** The previous revision claimed that writes through any open descriptor survive; with a trash that is reclaimed after a while, that claim cannot hold (review D3), so the guarantee is scoped. The no-lost-bytes guarantee covers every write that reaches the file before step 4's comparison, and every write through a descriptor opened after the effect. That includes programs that save by writing a temporary file and renaming it into place, which is how most editors save, and programs that open, write and close. It does not cover a process that keeps a descriptor open across the effect and writes through it after step 4. Such writes go to the displaced file in the trash ([rename(2)](references.md#ref-rename): an open descriptor refers to the file, not the name), and are kept only as long as that trash entry is: the retention period, or until the size cap evicts it. Before reclaiming a file, the collector compares it with the values recorded when it entered the trash, and turns a changed file into a recovered file instead. **[changed]** The collector compares a file's content, not its ctime, with the content the effect verified before trashing it, and only a different size or content counts as a change (GUN-317). A change of metadata alone, such as `chmod -R` on the linked folder or a copy of the folder to another disk, also changes ctime, and with ctime every file deleted that week would come back at the root on every device. That check is best effort: a write between the check and the unlink is lost. The trash keeps its own index of those recorded values, since the effect record is gone by then. Native tests (§7.4) include reclamation by expiry and by the size cap.

**Ordering.** The staged file is flushed before it is renamed into place. After every rename, the driver flushes both the source and the destination directory, in that order, since a cross-directory rename changes both ([Pillai et al. 2014](references.md#ref-pillai)); the store transaction that acknowledges the effect comes after the last flush. On macOS, `fsync` does not ask the drive to write its cache, so power-loss durability needs `F_FULLFSYNC` ([Apple fsync(2)](references.md#ref-fsync-apple)); the driver uses it for the staged file and both directories, at the cost of slower applies. Process-crash recovery needs none of this, only the order of the steps and the record.

The **local trash** (`.koidrive/trash/`) holds every entry the engine displaced, for a configurable period (proposed default 7 days) or until a size cap, whichever comes first; the cap can evict an entry earlier, so the period is a maximum, not a promise. It is a client-side safety net; the server's trash and version history remain the primary recovery path. A changed entry found at reclamation is recovered at the sync root rather than in its old folder, which may be gone by then, and an empty folder takes no room under the cap, so only the period reclaims it.

### 5.3 Recovery, partial downloads and uploads

**[changed]** After a crash the driver recovers the effect in flight, if any, before it rescans. It does not need to know how far the effect got; it inspects the target, the staging path and the quarantine path, and every combination has one safe action:

| Found | Meaning | Action |
|---|---|---|
| a quarantine entry | the effect reached step 3 | Compare the quarantined entry with the expected state, whatever the target holds now. If it matches: when the staging file still exists and the target name is free, rename it into place; then move the entry to the trash and report `EffectDone` (or `EffectFailed` as overtaken if the staging file could not be placed). **[changed]** If it does not match: rename it back when the target name is free, otherwise make it a recovered file, and report `EffectFailed` |
| no quarantine entry, no staging file, target in the effect's final state (the new content, the moved entry, or absent after a removal whose entry is in the local trash under the effect's ID) | the effect finished | report `EffectDone` |
| **[changed]** no quarantine entry, no staging file, the entry a write replaced in the local trash under the effect's ID, and the target without the new content | the effect finished, and the user changed or removed the file it wrote | report `EffectFailed` as overtaken (see below) |
| no quarantine entry, anything else | the effect stopped before step 3, or the user changed the target | delete the staging file (server bytes, downloadable again) and report `EffectFailed`, so the next plan sees the current disk |

**[changed]** The second row judges the target by its name and content alone, so the engine takes `EffectDone` from recovery only when L confirms that the entry found is the effect's own (GUN-339, GUN-342). An entry that L holds as another node is that node's: a synced file that the user renamed onto the name of a download with the same bytes is not the download. A removal whose node L places elsewhere found the name empty because the user moved the node. In both cases the driver reports `EffectFailed`, as the effect would have failed had it met that state. **[changed]** L knows of a move only once a scan has seen it, and recovery runs before the rescan. So a removal that finds its name empty also needs its entry in the local trash: without one, the user moved or deleted the entry before the effect reached it, and recovery reports `EffectFailed` with the entry missing. Otherwise the rescan would take the moved entry for a new file and upload it beside the node (GUN-443).

In every row, quarantine is either moved to the trash after it has been verified as synced content, or returned to the user. In the first row, a staging file that is already gone was placed: when the target no longer holds the new content, the user changed the file it wrote, and recovery reports the effect as overtaken. **[changed]** A write is overtaken whenever the entry it replaced matched and went to the local trash while its target does not hold the new content: the user changed or removed the written file, or took its name before it was placed, during the effect or across a crash. An overtaken write leaves the node out of S and L, so R's content is downloaded again and what the user left on disk is kept beside it as a new file. S cannot stay at the content the write replaced: that content is in the trash, so the disk no longer shows the node and a rescan would take that for the user's delete. A later remote edit back to the replaced bytes would then look unchanged against S, and the device would delete or overwrite an edit it never saw, against R7 (GUN-582). Recovery writes the effect's counter to the marker again before it looks, since the crash may have come before the marker write. A crash during recovery repeats recovery, which is idempotent. Staging files with no effect record are deleted at startup: they can only hold server bytes. Verified chunks stay in the cache, so a download resumes. Uploads resume through `PrepareUpload`: chunks the server already has come back as `PRESENT` (spec §8 step 1).

### 5.4 Case sensitivity

The default macOS APFS volume is case-insensitive and preserves case; case-sensitive variants exist ([Apple APFS FAQ](references.md#ref-apfs)). Linux file systems are case-sensitive by default; ext4 can fold case per directory since Linux 5.2 ([Collabora 2020](references.md#ref-casefold)). The server enforces a unique `name_key` per directory on every platform (spec §6.1). Consequences:

- On Linux, `Report.txt` and `report.txt` in one folder cannot both sync. The second one committed gets a conflict name (R1), and the Linux device renames its local file to match. This is spec open question 3; the engine handles either answer.
- The engine decides whether a name is taken by `name_key`, never by asking the file system, so it behaves the same on both kinds of volume.
- A case-only rename (`a` to `A`) must reach the engine as a rename, not as a delete and a create; the fs layer recognizes it by file identity.
- **[changed]** A case-only or normalization-only rename that the engine applies goes through `.koidrive/parked/` in two no-replace renames, because on a case-insensitive volume the target name is already taken by the source itself.

### 5.5 Unicode normalization

APFS preserves the normalization of names and, since macOS High Sierra, compares them normalization-insensitively ([Apple APFS FAQ](references.md#ref-apfs)). HFS+ stores names decomposed (NFD). Linux stores bytes. The server stores NFC (spec §6.1). The engine keeps the exact on-disk name in L, so paths resolve, and compares names after NFC normalization, so an NFD name from HFS+ does not cause an endless rename. On Linux, two names that differ only in normalization collide in `name_key`, like a case collision.

Which names collide must not depend on the Unicode version a component happens to ship. The server (koidrive#6) and the engine both fold with the tables of CaseFolding 18.0.0 (statuses C and F). NFC is not pinned yet: the server uses the runtime's `String.prototype.normalize` and the engine a Rust crate, which can lag behind. Pinning both is a spec change (§10). Exact on-disk spelling and portable name equality stay separate: L keeps the spelling, comparisons use `name_key`. Native tests on real volumes (§7.4) cover NFC and NFD aliases, casefold collisions, an ignored file occupying a name, and two Linux names that map to one server key.

### 5.6 Symbolic links, special files and hard links

Symbolic links, sockets, devices and FIFOs are not synced in v0 (spec §5.1) and are skipped by `core/fs`. The engine never follows a link, so nothing outside the root is read or written through one. A remote file whose name is taken locally by a skipped entry cannot be applied; it is reported as a problem. Hard links are synced as independent files.

### 5.7 Permissions and the executable bit

Only the executable bit is synced (spec §5.1), as part of `Content`. Owners, groups, ACLs, extended attributes and macOS resource forks are not. A file the engine cannot read is not a deletion: it is reported as a problem and left out of planning until it becomes readable. A file the engine cannot write fails its effect and is reported.

### 5.8 Files that change while being chunked or uploaded

The fs driver records identity, size and mtime before reading a file and checks them again after chunking; if they changed, it discards the result and rescans after the file has been quiet for the debounce interval. Chunk bytes are read again when uploaded and must match their hash, which the server also checks (R2's `sha256` on relay uploads, spec §8 step 2). If the file changed after chunking, the upload fails, the commit gets `MISSING_CHUNKS`, and §4.2 abandons it and re-plans from the newer observation. A file that never stays still (a log or a database being written) is retried with backoff and reported as busy after a limit.

### 5.9 Very large directories and trees

The trees are indexed by `(parent, name)` and `(parent, name_key)`, so lookups do not scan siblings. Planning visits only dirty nodes. Commits are cut at 1,000 ops in dependency order; bootstrap reads `ListTree` page by page (spec §7.5). The initial scan streams entries to the engine in batches. v0 holds the trees in memory and persists changes row by row; a tree larger than memory would need the store to page, which is not planned for 0.1.0.

### 5.10 `.koiignore`

**[changed]** New section: the project owner decided that 0.1.0 ships a `.koiignore` file with `.gitignore` syntax and an empty default list (GUN-270). The rule that governs everything below: **becoming ignored never deletes anything, on either side.** An ignored path is outside the sync tree on the device that ignores it, and that device just stops syncing it. **[changed]** One exception holds until the guard of §6.1 exists: a move into an ignored path that a rescan cannot attribute to a rename, and whose identity the walk of the ignored subtrees does not find, counts as a deletion (GUN-305, the table below).

**Where it lives.** A `.koiignore` file can be in any directory of the space, like `.gitignore` ([git documentation](references.md#ref-gitignore)). Its patterns are relative to its directory and apply to that directory's subtree; a deeper file's patterns take precedence over a shallower one's, and within a file the last matching pattern wins. `.koiignore` files are ordinary synced files, so every device converges on the same rules. A `.koiignore` file in an included directory is never ignored itself, whatever its patterns say, so the rules cannot hide themselves. Rules inside an excluded subtree are not read, as in git, where patterns in an excluded directory have no effect ([git documentation](references.md#ref-gitignore)): a `.koiignore` file there is excluded along with its directory. The built-in exclusions of §5.1 (`.koidrive/`, platform files) apply in addition and cannot be negated.

**Syntax.** `.gitignore` syntax: blank lines and `#` comments, `!` negation, a leading or middle `/` anchoring a pattern to the file's directory, a trailing `/` matching only directories, `*`, `?`, `[...]` and `**`. As in git, a file cannot be re-included when one of its parent directories is excluded. One deliberate difference: names are matched after NFC normalization and case folding (`name_key`, §5.5), so a pattern means the same thing on case-sensitive and case-insensitive volumes. An unparsable line is ignored and reported as a problem on the `.koiignore` file.

**Who evaluates it.** The engine never reads file bytes, so the fs driver parses each `.koiignore` file it observes and passes its rules to the engine with the observation. The engine owns the matcher, so that it can apply the same rules to remote nodes; `core/fs` uses the same matcher to leave ignored paths out of scans and watchers. Rules come from the `.koiignore` files on this device's disk. When a remote change creates or updates a `.koiignore` file, the planner applies that effect before any other effect in the same directory's subtree, so new rules are in force before the nodes they cover arrive. **[changed]** After an effect that wrote, moved or removed a rules file, or that moved a folder, the driver asks for no further effect and no commit until a scan of the effect's paths has passed its rules: the engine holds each rules file by the path of its folder (GUN-305). **[changed]** A rules file is any file whose `name_key` is that of `.koiignore`, so `.KOIIGNORE` is one too, and the scans hold each folder's rules under the `name_key` of its path, as the matcher does: renaming a folder or its rules file only in case keeps the rules. A rules file that cannot be read (larger than 1 MiB, or not readable) keeps the rules its folder had. When the folder had none, the scan reports the folder as unreadable and leaves what it holds as it was known, so nothing the file may exclude is uploaded before it can be read (GUN-305). **[changed]** The driver passes every folder a scan reports unreadable to the engine, which plans no effect and no commit for a node that L, S or R places below it until a scan reports the folder's rules. It holds the folder by its node, which the driver finds after the batch's changes at the path the scan reports, by exact name as L holds names: a folder renamed, also only in case, is the same folder, and two folders whose names differ only in case, as a case-sensitive volume holds them, are two. The hold also ends when L no longer holds the folder. Each scan reports, apart from the rules files that changed, every folder whose rules it established, at the path where it listed the folder: it read the folder's rules file, found none, or kept the rules an earlier scan read. The hold of the node at that path ends there, whatever the rules file did meanwhile, so a folder renamed and emptied of its rules file while held is released at its new path (GUN-305). **[changed]** A folder that holds two rules files whose names differ only in case, as a case-sensitive volume allows, is reported unreadable the same way until one of them is gone, since either could be the one other devices keep (GUN-305). Until the first scan of a watcher has settled every scope, a folder that is still pending is reported unreadable too: the scan may have found it missing while listing and back while confirming, without reading its rules file (GUN-305). The rules are not part of the stored state (§2.8): after a restart the engine plans no effect and no commit until the driver has passed it the device-local list and the rules files of a full scan (GUN-305). **[changed]** The first batch of each watcher lists every rules file its scan read, and the engine drops the rules of every folder it does not list. This matters when the platform watcher fails and a rescanning one takes over: the new scans compare with no earlier rules, so they could not report a rules file deleted while events were lost (GUN-305). A stored node that is excluded would otherwise look like any other until the scan reached its rules file.

**Excluded nodes.** A node whose position in R, S or L matches the rules on this device is **excluded** here. **[changed]** So is a node whose place in L below its R parent matches them, where an effect would write it: L can name or place a folder differently from R, and the rules can exclude a local folder whose R path they include, as `ss/` excludes a local `ß`. And so is a node R holds below a folder that is excluded here for any of these reasons, so an excluded folder excludes what R holds below it (GUN-565). The engine keeps its S entry, freezes it, and plans nothing for it in either direction: no ops, no effects. **[changed]** One case comes before that rule: a node that L shows at an included position different from S's has been moved by the user out of exclusion on this device. It is not excluded; its move is planned against S like any local move, and it leaves exclusion once the result places it at an included position in R and S. A node whose local copy has not moved stays excluded, which keeps a remote move into an ignored path from moving the local copy. R keeps following the server. **[changed]** Freezing has two limits (GUN-305). S still takes what L and R both hold for the node, as for any node. And S gives up a position that neither L nor R holds any more: with the node in L and live in R, S takes R's position, or the local copy's when S cannot hold the node at R's (the folder R has it in may be one this device never synced), and keeps its content, so the content is still compared with the last synced one when the node is included again; otherwise S drops the node, which is then resolved like a node never synced. **[changed]** A folder that S drops gives up its S entry together with every node S holds below it, when all of them are ignored too: their entries would otherwise keep the folder's name in S for good, since none of them is ever planned (GUN-305). No op ever moves the S entry of an excluded node, so without this the name it holds in S would keep every other node from being acknowledged there. An excluded node is never parked. **[changed]** Parking never changes whether a node is excluded: the position L keeps for a parked node counts as its position in L, for it and for every node below it (GUN-536). A parked node leaves the parked directory for its position in R. It goes back to the position L keeps for it instead when R no longer holds it and the node has a change of its own (a parked node whose only change is that R deleted it is removed like any other), when the rules exclude it, when the local copy of an excluded node holds its name in R, or when it holds an edit and the rules exclude its position in R, where the edit would never be uploaded (GUN-540). A parked node the rules exclude whose local name the local copy of an excluded node holds goes to its R position instead, unless it holds an edit and the rules exclude that position too. An edited node is never parked to make room for another node while the rules exclude its R position, since it would only go back. A parked node holds no name on disk, so its S entry gives up its position as above even when another node has taken the old name. A parked node that can reach neither position stays in the parked directory and is reported as a problem once the effects have nothing left to do, so it is never left there unseen (GUN-540). **[changed]** A parked node whose only change is remote and whose place in R the local copy of an excluded node holds takes its R position as the one L keeps for it. S then follows R, and the old name is free for the nodes that wait for it, such as a folder R put in its place (GUN-473). A node whose place is held by the local copy of an excluded node cannot be put there, and it is not parked to make room for another node either, since it could not leave the parked directory again while the rules stay as they are. It stays where it is and is reported as a problem, and so does a node that waits for its name. An excluded node is not a deletion and never enters the mass-delete ledger. It is ineligible for convergence (§3.4), and its local copy, if there is one, is left exactly as it is.

| Situation | What happens on the device with the rule |
|---|---|
| A synced node becomes ignored (a rule is added) | It becomes excluded. Nothing is deleted locally or remotely; other devices keep syncing it. Local edits made while it is ignored are not uploaded |
| An ignored node becomes included again (the rule is removed) | The driver rescans the path; the node re-enters L with its kept S entry, and the normal classification of §2.3 resolves it: an edit made while ignored is uploaded, a remote change is downloaded, both are a concurrent change. A path that was never synced appears as a new local node |
| A remote node matches a local rule | It is not downloaded; it becomes excluded. For a directory, its whole subtree is excluded |
| The user moves a synced node into an ignored path | The fs layer reports the move from the rename (file identity), and the node becomes excluded at its last synced position: no op is sent, so the server and other devices keep it where it was. **[changed]** When events were lost and a rescan cannot attribute the disappearance to a rename, the fs layer does not report a deletion yet (review D4). It first looks for the entry's identity in the ignored subtrees, with a walk that only lists and stats: no file reads, no watches. Until the walk has decided an entry, the fs layer reports nothing for it: the entry leaves the scan's snapshot, which stays equal to the disk, and the walk holds it by identity at the path where L still has it, moved along by later renames. **Interplay with the guard.** Adding a rule, even `*`, excludes nodes and deletes nothing, so it never prompts. Removing a rule can make many files appear at once; they are uploads, not deletions. Only actual removals from disk count toward §6.1.
