## 4. The server's total order

### 4.1 Commit

1. The planner builds a commit (§2.6) and the engine persists it as in flight.
2. The net driver uploads the chunks the commit references (`PrepareUpload`, then `PUT` for each `UPLOAD`; spec §8 steps 1–2) and sends `Commit`.
3. The result updates R and S (§2.7) and the frozen nodes are released.

`base_seq` is `last_seq` at the moment the commit is built and is not changed on resend: the ops were built against that state, and keeping it lets the server detect every change committed after it (spec §6, "unseen change"). Only one commit is in flight (spec §8, last paragraph).

### 4.2 Errors and retries

| Outcome | Applied on the server? | Engine action |
|---|---|---|
| transport error, disconnect, timeout | unknown | Resend the same commit, same `commit_id`, after reconnecting and catching up |
| `MISSING_CHUNKS` | no (checked before any op, spec §8 step 4) | Upload again, resend the same commit. If the bytes are gone (the file changed since it was chunked), abandon the commit and re-plan from L with a new `commit_id` |
| `RETRY_LATER` | no | Back off for `retry_after_ms` and resend |
| `QUOTA_EXCEEDED` **[changed]** | no | With `retry_after_ms` above 0, back off for it and resend; without one, a policy halt |
| `READ_ONLY` (format too new, spec §9.2) | no | Abandon, stop committing, report a problem; downloads continue; a `Welcome` that allows writes ends it. **[changed]** Queued restores end as rejected (§2.6) |
| `FORBIDDEN`, `NOT_FOUND`, `CONFIRMATION_REQUIRED`, `UNSPECIFIED`, unknown code **[changed]** | no, or unknown | Policy halt (below) |
| `INVALID_ARGUMENT` **[changed]** | no | Policy halt, keeping the commit as evidence; this is an engine bug or a reused `commit_id`, and the simulation treats it as a failure |
| `UNSUPPORTED_VERSION`, `HEAD_MOVED` | no | Abandon and re-plan with a new `commit_id` |
| `LIMIT_EXCEEDED` **[changed]** | no | The commit's change records or its result do not fit in one 1 MiB message (spec §7.2). Abandon and re-plan in commits of half as many ops; a commit of one `Delete` is re-planned as deletes of the folder's contents first, a commit of one `Restore` ends that restore as not fitting, since the nodes it brings back are too many or too deep for one commit, and any other single op marks its node as a problem. Each acknowledged commit doubles the op count back towards 1,000 |
| `base_seq > head_seq` | no | Resync (§4.4), then re-plan |
| history mismatch (proposed fence, §10) **[changed]** | no | Stop committing; the space enters recovery as for `HISTORY_CHANGED` (§6.4) and the commit is kept as evidence |
| `STALE_DEVICE_STATE` (proposed, §10) **[changed]** | unknown | Stop committing; recovery (§6.4) |

**[changed]** A **policy halt** (RFC 0006 §1) keeps the refused commit with its `commit_id` and slot and records the code. The engine sends nothing more to the space, neither that commit nor a new one, and downloads continue. The refusal is reported to the user with the code and the error's message. The halt is stored, so it outlasts a reconnect and a restart, and no `Welcome` lifts it, so it overrides the resend of §2.8. A `Welcome` with *w* < *a* is a loss under the halt too, and is handled as in §2.8 while the halt stays: *a* := *w*, the refused commit is dropped, since its slot no longer follows the server's count, the seqs kept for the slots above *w* are dropped, and R is listed again (§4.4). Without the listing, a device whose cursor the restored server's head has passed would follow the log over its lost changes. A later `Welcome` then finds *w* = *a*, so the loss is handled once and changes other devices make afterwards are not taken for lost ones. A `Resend` lift after such a loss has no commit left to send, and its changes are planned again. Only a user action or a client update that knows the code ends it; RFC 0006 leaves those actions to a later RFC. It differs from read-only, which follows from the device's format or role and ends with a `Welcome` that allows writes.

A commit is abandoned only after an error that proves it was not applied. **[changed]** An earlier revision also abandoned a commit whose outcome was unknown and re-planned it from the trees. That is unsafe (review D1): if the commit wrote B and another device that had seen B then deleted the node, re-planning finds a local edit against a remote delete and revives the node. An outcome that is unknown is resolved by the stored result, never by inference from the current tree; when it cannot be resolved (another history, or a store older than the device's history), the space enters recovery (§6.4). Abandoning means forgetting the in-flight record; S was not changed for it, so the same local changes are planned again from the trees.

### 4.3 Rebase

"Rebase" here means what §2.4 describes: local changes are kept as tree differences rather than queued ops, so after new remote changes arrive the next commit is simply built from the new R, with concurrent changes resolved first. There is no op log to rewrite. The two places where a sent op does need to be rewritten are handled by the result codes: `MERGED_INTO` (the client re-keys the folder) and `CONFLICT_COPY` (the client re-keys the file). Both happen once per commit and touch only the nodes named in the result.

### 4.4 Receiving changes

- After `Connected`, the engine first compares `Welcome.history_id` with R's. **[changed]** If they differ, the space enters recovery (§6.4) before any bootstrap or planning, so R, S and L are kept as evidence instead of being replaced. Otherwise it sends `Resume{history_id, since_seq: last_seq}`, unless `last_seq` is above `head_seq` or below `log_floor_seq`; then it bootstraps with `ListTree` (spec §7.3–7.5).
- **[changed]** Records are applied as whole commits in contiguous seq order: commit `last_seq + 1`, then the next. A commit at or below `last_seq` is a duplicate and is skipped. A gap (a commit above `last_seq + 1`) triggers a new `Resume` and the rest of the batch is dropped. Within an applied commit, each `NodeState` overwrites the stored node only if its rev is above the stored one (spec §5.2), which makes the overlap between a bootstrap listing and the log replayed after it harmless. Rev gating is not a licence to apply commits out of order (review B7): `NodePurged` has no rev, so a purge followed by an older `NodeState` would recreate the node, and a post-image can name a parent created by an earlier commit that has not been applied yet.
- **[changed]** The device's own commit results arrive in `CommitResult`, not as pushes (spec §7.3 step 2), but a log replay after a reconnect includes the device's own earlier commits like any other. A result is acknowledged as §2.7 describes: at once when its seq is `last_seq + 1` or already covered by R, after the gap is filled when it is further ahead. So R never gains a node whose parent is missing, and an own commit is never left in flight because its records arrived first.
- The engine is **caught up** once `last_seq` reaches the `head_seq` of the last `CaughtUp`. It builds commits only when caught up, so local changes are rebased onto everything the server had when the session began.
- An unknown change record type means the client cannot keep the tree correct: the engine stops applying, stops committing, and asks for an upgrade (spec §9.1, fail closed).
- Bootstrap after `LOG_TRUNCATED` or `AHEAD_OF_SERVER`: the listing (spec §7.5) is collected into a staging tree while the old R stays in use. Pages are read at different `head_seq`s, so a page can hold a node whose parent was trashed or moved by the time another page was read. **[changed]** The staging tree replaces R only after the log has been replayed up to the highest `head_seq` of any page and the result is a valid tree; until then the planner does not run. Then S and L are kept, and the normal classification decides what moves in which direction. **[changed]** When the server reports `AHEAD_OF_SERVER`, in `ResyncRequired` or by refusing a commit, or `Welcome` reports *w* < *a* (§2.8), it lost commits this device applied. **[changed]** The cursor keeps the commit token at `last_seq`, and each `Resume` and `Commit` names the token at its seq (RFC 0013). So a server whose head other devices have brought back up to `last_seq` after a loss still answers `AHEAD_OF_SERVER`, instead of continuing the log over a seq it gave to another commit (GUN-423) or taking a commit built on that seq (GUN-454). The store records this with `last_seq` until the bootstrap replaces R, because the listing cannot show it: another device may commit before the listing begins, so the server's head is no longer below `last_seq`, and the device may restart in between and see no `AHEAD_OF_SERVER` at all. S then forgets each node that the new R lacks or holds live with another shape, and every node S holds below one. A node L still holds is created again instead of being taken for a remote delete, and a file whose content differs from R's is kept as a conflict copy (§2.4) instead of being replaced by R's older content. A node in R's trash keeps S and stays a remote delete, also below a node S forgets, except a file whose edit was lost (below): S forgets such a folder only once the delete has taken what it held, through a waiting update (§2.7) that the effects never take for a remote delete, and the folder is then created again. **[changed]** Each waiting update (§2.7) records the slot of the commit whose result made it. At a loss, an update from a slot above *w* is dropped, so S keeps what it held: when R holds the node as S does, the change is sent again, and otherwise S forgets the node, as for any node R holds with another shape. An update from a slot at or below *w* stays, so a change another device made since, before or after the loss, is taken as a remote change once the update fits. An update no commit made, such as a Discard's, stays too. That holds for a node R holds in the trash too. A lost update kept there would stand in for S in the effects, so content another device restores would replace an edit only L holds, and later commits take its slot again (GUN-418). An effect that waits an update again keeps the update's slot. **[changed]** A position L and R agreed on while the commit in flight was out (§2.7) is kept only where the restored server still holds the record that showed it: one of a seq at or below that of the newest commit of this device the server still counts (the bound below), or one the new R holds the node at, live and at that revision. A later commit can take a lost record's seq, so a revision comparison cannot show that the record survived, and any other agreement is dropped and taken again from L and the new R (GUN-457). **[changed]** This listing also reads the trash: every `ListTrash` page after every `ListTree` page, merged by rev like the replay, which only ends once it reaches the `CaughtUp` sent after both (RFC 0002 §6). So a node another device trashed after the loss counts as trashed, not as lost, and is not created again under an ID the server holds in its trash, which it would refuse with `ID_EXISTS`. **[changed]** A delete this device made in a lost commit is sent again. The engine records each node a delete of this device trashed, with the seq of that delete's commit, for as long as R holds the node trashed by that commit. The restored server can give later commits the seqs the lost ones had, so a seq below the lost delete's does not show that a node state is older than the delete. The engine therefore also keeps the seq of each of its last 1,000 acknowledged commits by slot. The newest slot the server still counts (*w*, §2.8) is a commit the restored server holds, so every seq at or below its seq is from before the loss. When the new R holds a recorded node live with the shape it was trashed with and no revision above that bound, and neither L nor S holds it, S takes R's shape, parents first, so the node is a local delete and is planned again. Otherwise it is downloaded, since another device changed it or a person restored it after the loss, or the bound is unknown, and the delete never removes what the deleting user did not see. The keep rule of §2.4 and the server's R7 cover changes made after the listing. **[changed]** An edit this device made in a lost commit is sent again the same way. The engine records each file whose content an edit of this device set, with that commit's seq, for as long as R holds that content. When the new R holds such a file, live or in the trash, at the position S holds, with content of no revision above the bound or at a version the log replaced for it (below; GUN-579), S takes R's shape, so the content L holds is a local edit and is sent again instead of being kept beside R's as a conflict copy. A delete R holds then trashed the content from before the edit, so the edit beats it (R8, §2.4): the server revives the file, and the edit does not go to the local trash (GUN-385). The engine cannot tell whether the deleting device saw the edit. A device that downloaded the edit before the loss and deleted the file after it, or deleted the file and the conflict copy holding the edit (GUN-389), has its delete undone the same way. This is a deliberate trade-off: the revived file can be deleted again, while an edit that went to the local trash would be missing from the server and from every other device. **[changed]** A user who edits a file back to the bytes the restore rolled it back to would lose that edit too. The engine tells contents apart by their bytes, so L and R agree once S forgets the file, and the author's resend of the lost content would replace the edit. So when L holds the bytes the new R holds for a file and either S held other content or this device's edit of the file was in a lost commit, the store records the file as holding an edit the server does not have. A file the new R holds in the trash keeps S (above), so it is recorded when L holds content S does not: a device that restores it from the trash with L's bytes would otherwise make L, S and R agree. **[changed]** The same holds for an edit L makes later, while R still holds the file in the trash, so any edit L holds of a file in R's trash is recorded. While the record stands, the file counts as changed locally even where S and R hold the same bytes. It ends when the server acknowledges an edit or create of the file with the content L then holds, so an edit made while an earlier one was being sent stays recorded. The edit is sent as an `UpdateContent`, which gives the file a new version and content revision even for the same bytes, so the author's resend meets an edit it did not see and becomes a conflict copy (§2.4). A remote edit that arrives first, the resend included, makes the file a concurrent edit, and the edit is kept as a new file beside it (R3). The record ends when the server acknowledges an edit or a create of the file, or when L no longer holds the file. Further local edits before the commit keep it, and so does another device removing the file: the edit beats the removal, and the file is created again, as for any edit L holds (GUN-438). **[changed]** Another device that held the lost content sends it again the same way when it can show that the restored content is older than its own (GUN-389). The engine records, for each file, the version IDs R held for it before its current one as the log moved R forward, the newest 64. A listing records none, since it can take R back to a version a lost commit replaced, and keeps only the recorded IDs up to the one it lists. A server never gives a version ID to two versions, also across a loss, and a `Restore` of a version makes a new one (RFC 0016). So when the new R holds a file live at the position S holds, at a recorded version, and L and S held R's content before the bootstrap, nothing changed the file after the loss: S takes R's shape, and the content L holds is sent again as an edit. Any other content may be an edit another device made after the loss, and the file is kept as a conflict copy. The author's resend and this one can both reach the server. The second meets unseen content equal to its own, which the server applies without a change (RFC 0016), so neither leaves a copy. A device whose user edited the file to the restored bytes after the loss records that edit as above, so the resend meets an edit it did not see. So does a device that holds this resend when its user edits the file to S's bytes, which ends the resend. A log record that gives R the bytes S holds, while L holds a change, is a remote edit that the bytes cannot show, such as another device's resend of an edit back to the restored content. S forgets the file, so L's change is kept beside R's as a conflict copy instead of replacing it. **[changed]** A delete that another device makes after the loss beats a resend that holds no change of this device's user: this content resend, and the create or move of a node S forgot that L holds as S did, such as a file under a folder whose lost move is sent again. The engine records each such node, unless one of its own commits made R's record of it, until the server takes the resend, S takes L's shape, or L changes the node. When R holds the node, or a folder L holds it under, trashed before then, S takes L's shape and the file's unsent-edit record ends, so the delete reaches L (GUN-548). A commit that carries such a resend sets `require_head` (RFC 0002 §4), so a delete the server takes first refuses it with `HEAD_MOVED`, also when the commit was built before the delete reached this device, and the device plans again once R holds the delete. **[changed]** A content resend carries `resend` on its `UpdateContent` (RFC 0018), and the author's own send of its lost edit never does. The server moves `content_rev` for a resend but leaves the file's edit revision, which R7 reads, so a delete the server takes after the resend, built without it, trashes the file (GUN-552). The author's edit still beats such a delete: when another device's resend landed first, the author's equal send records an edit revision and revives a file a delete trashed. A device whose user deleted the file before the resend's log record arrived plans the delete against it: when the record moves only `content_rev` and S held R's shape before it, S takes the record's shape, so the delete goes out with a base past the resend. A later record that moves only the edit revision is the author's edit, so S forgets the file and it is downloaded again. `HISTORY_CHANGED` (a rewind or a point-in-time restore) is different and starts the recovery of §6.4.

### 4.5 What is not a CRDT

The Space DO is a sequencer and validator, and clients are replicas of its state machine. Clients never merge each other's ops, keep no vector clocks, and do not need to converge without the server. The conflict rules are not commutative: which side keeps the name depends on which commit came first (R1, R3), which is why the client must not resolve unseen conflicts itself. Offline devices keep working: their changes accumulate as differences between L and S, and they are rebased and committed when the device reconnects.
