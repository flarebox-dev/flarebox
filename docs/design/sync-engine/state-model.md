## 2. State model

### 2.1 Options

| Approach | How it works | Why not (or why) |
|---|---|---|
| Intent queue (Sync Engine Classic) | Persist "work to do": upload this, download that. Replay the queue after a restart | The queue drifts from reality when events are lost, a crash interrupts a step, or the disk changes while work waits. Dropbox's account of Classic names this as the root problem: it "persists the outstanding work", and a move became a delete plus an add, which loses the file everywhere when only the delete goes through ([Jayakar 2020](references.md#ref-nucleus); [Goldberg 2020](references.md#ref-trinity)) |
| Archive-based state sync (Unison) | Keep the last synchronized state as an archive; compare each replica with it per path to find changes ([Pierce and Vouillon 2004](references.md#ref-unison), §5) | The right core idea (the archive is a merge base), but Unison is path-keyed, two-replica, batch, and stops at conflicts for a person to decide. Koidrive has N devices, stable IDs and an unattended daemon |
| Peer-to-peer tree CRDT | Replicate an op log with timestamps; undo, apply and redo to reach the same tree on every replica ([Kleppmann et al. 2021](references.md#ref-move)) | Unneeded: a Space DO already orders every commit, so a replicated move operation buys nothing here. Content handling is not the reason: a CRDT can keep concurrent contents (a multi-value register does), as Koidrive does with conflict copies (spec §6.2 R3) |
| **Three trees (Nucleus)** | Persist observations: remote tree, local tree and synced tree per node. A planner derives what to do from their differences and stops when all three are equal ([Goldberg 2020](references.md#ref-trinity)) | **Chosen.** The direction of every change is unambiguous, a restart only needs a rescan, the stop condition is checkable, and the trees give strong invariants to test against |

### 2.2 The trees

All three trees are keyed by `node_id` (spec §2) and share the root node (`node_id = space_id`). Each is a valid tree on its own: every non-root node has a parent that is a directory in the same tree, there are no cycles, and in R and S no two live children of a directory share a `name_key` (spec §6.1).

- **R, remote tree**: the `NodeState` records (spec §5.2) this device has applied, including trashed nodes and their revs, plus `history_id` and `last_seq`, the highest seq up to which every record has been applied. A trashed node counts as absent when trees are compared.
- **L, local tree**: the disk as last observed. Each node has parent, exact on-disk name, kind, `Content` for files, and the file identity from `core/fs` (`dev`, `ino`, birth time) that lets the engine tell a rename from a delete and create. A node may be **parked** (§2.5): temporarily moved into `.koidrive/parked/` to break a dependency cycle; a parked node keeps its S position for comparison.
- **S, synced tree**: per node, the shape (parent, name, kind, content) on which L and R last agreed. S is the merge base: L ≠ S means a local change, R ≠ S means a remote change.

Names are compared after NFC normalization; whether a name is taken is decided by `name_key = NFD(casefold(NFD(name)))`, canonical caseless matching, so canonically equivalent names that differ only by case collide (spec §6.1, as the server implements it), on every platform, so the engine never relies on the local file system's case rules.

Besides the trees the engine persists:

- the **commit in flight** (at most one, spec §8): `commit_id`, its `device_seq` (§2.8), the `history_id` and `base_seq` it was built against with the commit token at `base_seq` (RFC 0013), the ops, for each op the shape it sent, and, once received, a result that cannot be applied yet (§4.4). **[changed]** The `history_id` was not recorded before;
- the **effect in flight** (at most one in v0): the effect record of §5.2. **[changed]** Effects were not persisted before;
- the **mass-delete state** of §6.1: the deletion ledger, the held nodes and the pending question. **[changed]**
- the **restores** a person asked for (§2.6, §6.3): each one that has no outcome yet, under the ID of its request, and the outcomes of the last 1,000 that ended. **[changed]**
- the **pending names** (§2.6): each node this device sent under a pending name, with that name and the name it takes later, while R holds the node at the pending name, live or in the trash, checked after the records of each commit, and until a move of this device that takes it off that name is acknowledged. **[changed]**

Nodes the in-flight commit touches are **frozen**: the planner neither changes them on disk nor rebases them until the result is applied.

### 2.3 Classifying a node

The planner looks only at **dirty** nodes, those whose L, S or R entry changed since they were last found in sync. Planning cost is proportional to the amount of unsynced work, not to the tree size.

| L vs S | R vs S | Meaning | Action |
|---|---|---|---|
| equal | equal | in sync | none; the node leaves the dirty set |
| equal | differs | remote change | apply R to disk (§2.5) |
| differs | equal | local change | upload as ops (§2.6) |
| differs | differs, L = R | both sides made the same change | S := R |
| differs | differs, L ≠ R | concurrent change | rebase on the client (§2.4) |

These rules are the B&P reconciler requirement in ID form ([Balasubramaniam and Pierce 1998](references.md#ref-bp), Definition 4.1.2): a node that is not dirty on one side takes the other side's value, and a node dirty on both sides is never overwritten by the synchronizer.

**[changed]** S := R for a node both sides changed the same way can wait, because S stays a valid tree (§2.7): its new name may still be held in S. S then takes R's content at once and the position once it fits, so the next edit on either side is compared with the content both sides already hold and is not taken for a concurrent one. A node whose acknowledged update waits keeps that update instead.

### 2.4 Concurrent changes the client resolves

The client commits with `base_seq = last_seq`, which tells the server "I have seen everything up to here". A local change, though, was made against S, which may be older than R. If the client sent it unchanged, the server would treat the newer remote change as seen and apply the local change on top, losing the remote one. So before building a commit, the client rebases each concurrent change onto R with the same outcome the server would choose if it had not been seen (spec §6.2):

| Local (L vs S) | Remote (R vs S) | Client action | Matches |
|---|---|---|---|
| content edit | content edit | Fork: the local file becomes a new node Y with the local content (CreateFile under the original name). The server renames Y with a conflict name because the original holds the name; the original node is downloaded again with the remote content | R3, R1 |
| content edit | rename or move | Send the edit; both apply | R4 |
| delete | any change (content, move, rename, or a new child) | Keep: drop the delete for that node and every ancestor that is still needed, set S := ⊥ for them so they are downloaded again. Delete only the nodes that did not change remotely | R7 |
| content edit or move | delete (trashed) | Send the op; the server revives the node and the ancestor chain it needs | R8 |
| move | move | Send the move; the later commit wins | R5 |
| move that would create a cycle against R | any | Revert locally **[changed]**: the node is reverted (§2.6), S is unchanged, and the effects move it back to its R position | R6 |
| create | create of the same name | Send the create; the server renames a file (R1) or merges a directory (R2) | R1, R2 |

Conflicts the client has not seen yet, because they were committed after `base_seq`, are resolved by the server with the same rules. Between the two, every concurrent pair is resolved exactly once.

### 2.5 Applying remote changes to disk

For a node with a remote change and no local change, the planner emits one **effect**:

| Remote change | Effect | Expected state the driver verifies (§5.2) |
|---|---|---|
| new directory | `CreateDir(path)` | parent has the recorded identity; the name is free (no-replace create) |
| new file | `WriteFile(path, content)` | as above; the content is fully downloaded and verified in staging |
| content change | `WriteFile(path, content, replaces)` | the displaced file, once quarantined, has the identity and content `replaces` (S's content) |
| move or rename | `Move(from, to)` | source has the recorded identity; the target name is free (no-replace rename) |
| trashed file | `RemoveFile(path)` | the quarantined file has S's content |
| trashed directory | `RemoveDir(path)` | the quarantined directory is empty, or holds only platform files (§5.2); children are removed first, bottom up |

**[changed]** Before d37ee0d's review the driver checked a precondition and then replaced or removed the target, which leaves a window in which a user write is lost (review B1, B2). Now every effect that displaces something goes through the quarantine protocol of §5.2: the displaced entry is first renamed into `.koidrive/quarantine/`, then compared with the expected state, and only an entry that matches goes to the local trash. Paths are computed from L at the time the effect is emitted, and the effect record is persisted before the effect is handed to the driver. A mismatch means the user changed something: the driver puts the entry back, reports `EffectFailed` with fresh observations, the engine updates L, and the next plan sees a local or concurrent change instead. The engine never retries an effect blindly and never emits an effect for a node with a local change. In v0 at most one effect is outstanding at a time; batches of independent effects (siblings, different subtrees), as Nucleus runs them ([Goldberg 2020](references.md#ref-trinity)), are a later optimization.

Some remote states cannot be reached one move at a time: two files swap names, or a directory moves under its former child. When no remote move is applicable but some are pending, the planner **parks** one blocking node: it moves it into `.koidrive/parked/<node_id>`, which is always possible, and moves it to its final place later. Parked nodes are excluded from local-change detection, and the rescan after a crash finds them there and puts them back into L instead of treating them as deleted. **[changed]** A reverted node (§2.6) that blocks another placement is parked like a node whose only change is remote, so two reverted nodes that hold each other's names are placed one after the other; parking moves an entry whole and never changes its content. A parked reverted node that R no longer has and that holds no unuploaded edit is removed from the parked directory. A parked node that R no longer has and that holds such an edit, reverted or not, becomes a new node and is moved back to its local position, so the edit is uploaded as a create. Parking usually freed that name for another node, and while an entry holds it, while R gives it to another node this device does not exclude, or while L no longer holds the folder, the move back is not made, so the new node is created from its local position while still parked, and the effects then move it to the position R gives it. A parked file re-keyed this way keeps its entry's name in the parked directory, the ID it was parked under, until it leaves the parked directory; effects address it by that name. A folder L deletes while a node under it is parked is reverted, so it is created again and the node is moved out into it. A node whose S update waits (§2.7) is not planned, so when it blocks a placement it is parked too, and the effects then place it at its R position; a local rename it held onto a name another node needs is not kept.

### 2.6 Building a commit

When the device is connected, caught up (§4.4) and has no commit in flight, the planner turns local changes into ops:

- New nodes become `CreateDir` or `CreateFile`, parents first.
- Position changes become `Move`.
- Content changes become `UpdateContent`.
- Deleted subtrees become one `Delete` per topmost deleted node, after the keep rule of §2.4 and the guard of §6.1.

The planner orders ops by simulating them on a scratch copy of R: it repeatedly emits an op that is valid there (parent present, name free, no cycle; a delete only when no surviving child remains under it) and applies it. **[changed]** When no op is valid, the planner looks for a **name cycle**: moves that each wait only for a name held by a node whose own move is in the cycle, as in a swap or a rotation through a third name. It moves one node of the cycle to a free pending name under its target folder (`<name> (pending)`, chosen as for a `CreateDir` below), which frees its old name, and the simulation goes on: the other moves become valid, and the node moves from the pending name to its target last. The ops apply in order and the change records hold each node's final state, so other devices never see the pending name, and every node keeps its identity and exact name. A cycle is sent only when the commit has room for all of its moves; a cycle longer than a commit can hold is split, and the moved-aside node keeps its pending name until a later commit, as a pending folder does. A move that waits for a name held by a node that does not move away is a real conflict and is still sent at the end for the server to resolve (R1 renames one side). **[changed]** A `CreateDir` sent this way may be merged into the folder that holds its name, so a delete of that folder or of a folder holding it waits for the next commit; otherwise the delete would remove what the merged folder brings. When the node holding the name, a folder or a file, is itself moving away, the new folder is created under a free pending name instead (`<name> (pending)`, or `<name> (pending 2)` and so on when that is taken, with the name cut at a character boundary so that its NFC form fits in 255 bytes) and renamed in a later commit. **[changed]** The commit layer records each node it leaves at a pending name, with the name L gave it, for as long as R holds the node at that name (GUN-514). So the rename is sent even after L has lost the name: when the keep rule (R7) brings back a folder the person deleted because another device changed something inside it, the effects download it at the pending name, and once L, S and R all hold it there the commit renames it to its own name, and the effects follow the result. So it is not merged into a folder that leaves, and the server does not rename it beside a file that leaves, as when a file moves into a new folder that takes its name. A move that would close a cycle against R is not sent: the node is **reverted**.

**[changed]** A reverted node is one whose local position the server will not take: a move that closes a cycle (or that the server rejects with `CYCLE`), a create or move the server renamed (§2.7), and a folder merged into one that L holds elsewhere with the nodes created in it (§2.7). The planner sends no create or move for it but still sends its content edits and a delete the user makes, and the effects of §2.5 make its position on disk equal to R as for a remote change, but never replace its content. When R no longer has it, the effects remove it only if it holds no unuploaded edit; a file that holds one becomes a new node, and the edit is uploaded as a create, because an edit beats a delete. A reverted node that the server lost, so that R does not hold it at all, stops being reverted when S forgets it or drops its waiting update (§4.4): the rename or merge that reverted it was lost too, so it keeps its ID and is created again at the position L holds, as another device that held it creates it again. A folder L deleted on the way from a reverted or parked node to the root is reverted too, so it is created again, and so is a folder the keep rule cannot clear from S yet because S still has children under it. A node stops being reverted once L has it at its R position. A create whose parent is not on the server and not in this commit waits for a later commit. A commit holds at most 1,000 ops (spec §13); the cut respects parent-before-child order. **[changed]** Its change records and its result must each fit in one 1 MiB message (spec §7.2), so the planner also stops at an estimate of 512 KiB of change records, counting a record for every node an op changes with its name and content, and a delete whose subtree exceeds that estimate is planned as deletes of the folder's contents first, deepest first, with the folder itself deleted in a later commit. The estimate is rough; `LIMIT_EXCEEDED` (§4.2) splits further.

**[changed]** A restore a person asked for (§6.3) leaves no difference between L and S: a trashed node is on no disk, and an earlier version is in no tree. So the engine keeps each request as an explicit intent, queued under the request's ID, and the planner adds a `Restore` op for it:

- The queued restores come first, in request order, so the first commit with room carries them and local changes of other nodes do not hold them back.
- A restore follows every op the commit has for its own node. An unsent edit of a file is therefore sent before the restore of an earlier version and becomes a version itself instead of a conflict copy, and a node deleted here is deleted before it is restored. While such an op is left for a later commit, the restore waits with it. It also waits while the planner leaves its node out: a problem node (§2.7), a node whose S update waits, or a parked one. The changes of such a node are unsent, and a restore sent ahead of them would be replaced by an edit the person made before asking for it. And it waits while L and R agree on its node but S has not taken that yet (class Same, §2.3), which happens when the S update depends on another node's effect. Sent then, the restore would change R while L still differs from S, and the engine would upload what the disk holds over the restored version as if the person had written it.
- A restore from the trash of a node R holds as trashed places the node in the scratch copy, at the position the request names or at the one it was trashed at. A folder is then not deleted in the same commit, because the delete would trash the restored node again; the keep rule of §2.4 brings the folder back after the commit.
- The estimate counts a record for every node R holds in the node's trash group, or one record when R does not hold the node as trashed.
- The engine does not judge a restore against R. R may lag the listing the person chose from, and after a bootstrap it does not hold the trash, so the server answers every case (§2.7).

A commit may hold only restores. A queued restore stays queued while committing is halted for recovery or by a policy halt; on a read-only device it ends as rejected, because nothing would ever send it.

The commit is persisted as in flight, with a fresh `commit_id` and the current `history_id`, before `SendCommit` is emitted.

### 2.7 After a commit result

The result's change records update R like any other record, and like any other record they are applied only in seq order (§4.4). **[changed]** Applying a result's records to R and **acknowledging** the commit are separate steps (review B7, D2). Acknowledging means making the S and L updates below, including any re-keying, and clearing the in-flight record, in one store transaction. A result whose seq is `last_seq + 1` is applied to R and acknowledged at once. A result further ahead is stored with the commit in flight; its nodes stay frozen, and it is applied and acknowledged once the commits before it have been applied. A result whose seq is at or below `last_seq` is not an error: R already holds its records, because the log replay after a reconnect or a bootstrap included the commit before the result arrived. Its records are skipped and the commit is acknowledged at once. S is updated from what was sent, not from what the server returned, so any difference between the two shows up as a remote change and the disk follows the server:

| Op | Result | S | L |
|---|---|---|---|
| CreateDir, CreateFile n | APPLIED | S(n) := sent shape, unless L and R agreed on a position at a revision of R after the result's seq, as for Move APPLIED: S(n) then takes that position. No earlier record holds n, so only a later move by another device or this one can give n such a position. When S cannot hold that position once the acknowledgement's other updates are made, because another node holds its name or its parent is gone, S(n) takes the sent position and the agreed position waits as n's S update while L or R still holds n there. n's position is not planned while it waits, so its sent position never goes out over a later move by another device, while an edit L makes at the agreed position is planned as below, and S takes the agreed position once it fits, as when the node holding the name is rebased. Agreed positions that only fit together, as in a swap, are made together when another update of the acknowledgement does not fit. A position only R came back to is a remote change, so S(n) takes the sent position and the effects follow R. A position from an earlier record does not count, because the server applies a move whatever other devices did after `base_seq` (last commit wins, §3.6), so the commit replaced it. **[changed]** A `Restore` op is the one op whose result sets nothing from what was sent. What it sent is an instruction, and only the server knows which nodes the trash group holds and what the version's content is. So everything it brought back is a remote change: R holds it once the result's records are applied, and the effects of §2.5 create the folders, download the files, or replace the file whose version was restored. The outcome is saved by the transaction that clears the commit in flight, so a restore is neither lost nor sent a second time.

**[changed]** S stays a valid tree. An S update above that would orphan a node, take a sibling's name key or close a cycle waits and is made together with the updates it depends on, including the updates of §2.4 that both sides agree on; a node with a waiting update is not planned until it is made, unless L edited it, or moved it away from the waiting position while R still holds it there. Such a node is rebased and planned against the waiting shape, also when R changed its content. An edit L made is uploaded wherever R holds the node, even when the node it waits behind is a problem node that never moves, and a move is planned because the update may never fit while L holds the node elsewhere, as when a folder R trashed takes its name key in S and L cannot remove that folder while the node is inside it. Until then the waiting shape stands in for S when the engine asks whether L holds an unuploaded edit, so when R drops such a node the effects remove it if it holds none, and the commit layer makes it a new node if it does, as for a reverted node (§2.6). For the same reason the effects compare L and R with the waiting shape, not with S. A node whose L matches S but not the waiting shape is not changed only remotely, so its content is never replaced, also when the node is moved because it is reverted or parked. A node whose L still holds the waiting shape while R differs from it is changed only remotely, and the effects give it R's shape. That ends an update that could never fit while L held its shape, such as a conflict copy whose sent name a new folder of the same name key took in S. A failed effect on a waiting node blocks it until the effect planned for it changes, as for any other node. A waiting update is dropped once anything else sets S for the node, such as settling a change both sides made alike or the keep rule of §2.4 bringing back a node L deleted, and once neither L nor R holds the node. A waiting removal is also dropped, even while R holds the node again, once something S holds under the node will not leave it with L's commits, such as a reverted node that R holds there: the removal could never be made, and the keep rule brings the folder back for that node. The keep rule also compares R with the waiting shape, so a node R holds as the update left it has no remote change to keep. Its position is stale once R no longer has the node there and L has left it too: it then falls back to the position S holds, so both sides' positions are compared with the S they came from, while its content stays the base for a later edit. Waiting updates that fit are made even while committing is halted, since downloads go on. Otherwise a stale update could hide a later local edit or hold the node out of planning for good.

**[changed]** **Conflict questions** (GUN-395). An `UpdateContent n` answered with `CONFLICT_COPY Y`, and a file this device created or moved that the server answered with `APPLIED_RENAMED` because a file `n` already held the name, open a question about the pair: `n` is the original, `Y` or the renamed file the copy. A create sent because the person answered Publish to a first link's question (§6.4) opens none: that answer already keeps both files. The commit layer records the entries that answer released, persisted until the server applies their create, so this holds when their creates span several commits or a commit is forgotten and planned again; a later move of such a file that takes a conflict name asks as any move does. The question records both node IDs and their revisions in R. It holds nothing, so both files keep syncing, and it is persisted with the other open questions (§6.1). Only the device whose write the server turned aside asks. Before each commit, and whenever such a question is open, the engine compares the pair with R and L. When R no longer holds either file live with the meta revision it was asked with, or L moved or deleted either file that S, or its waiting update, holds, someone renamed, moved or deleted a file by hand, and the question ends. When R holds another content revision of either file, the question is asked again under a new ID, and an answer to the old ID changes nothing. Keep both ends the question. Keep the original sends `Delete(Y)`, so the copy goes to the server's trash. Keep the copy first sends `UpdateContent n` with `Y`'s content, so `n`'s own content stays in its version history. Once that result has arrived and the download of §2.5 has brought the new content to L, it sends `Delete(Y)`. **[changed]** Each `Delete(Y)` requires `n` live at the revisions R holds for it when the commit is built (RFC 0015), so another device that renamed, moved or deleted `n` before the delete arrived keeps `Y`: the server answers `SUPERSEDED` and trashes nothing (GUN-464). An applied `Delete(Y)` also counts as this device placing `n`, so a `Delete(n)` another device built before the answer keeps `n` (R7). The record of `Y` as trashed here (§4.4) keeps `n`'s ID, so a `Delete(Y)` sent again after the server lost the commit carries the same precondition at the revisions R then holds, and none is sent once R no longer holds `n` live. Each answer sends one op per commit, so it fits after `LIMIT_EXCEEDED` has cut the op count to one, and a build sends no op for a node another answer in it already took. The engine sends them only while L, S and R agree on both files, and it leaves S as it is when the result arrives, so the disk follows as it would follow another device's edit and delete: the effects of §2.5 change or remove a file only while it is the one L and S hold, and a file the person edited in the meantime is kept (R7). Only an op of exactly that shape counts as the answer's op when its result arrives: a `Delete(Y)`, or an `UpdateContent n` with `Y`'s content in R. The upload of an edit of `n` is acknowledged as any op is, and its new content revision asks the question again. The question closes once the server applied its `Delete`. Any other result clears the answer, and the driver shows the question again; when the server refused because a file changed, the next build asks it under a new ID. An `UpdateContent n` that the server turns into a conflict copy also opens a question about that copy. When R's records of `Y` leave out its chunk list (more than 16,384 chunks), keep the copy cannot be sent, so its answer is cleared.

### 2.8 Persistence and crash recovery

The store persists, per `handle` call and in one transaction: R with `history_id`, `last_seq` and whether the server reported that it is behind `last_seq` (§4.4), S, L with file identities, the commit in flight (with its `history_id`, its `device_seq` and any buffered result), the accepted device counter, the effect in flight, the mass-delete state, the waiting S updates with the slot each came from, the nodes recorded as trashed or edited here and the seqs of the last acknowledged commits by slot (§4.4) **[changed]**, parked nodes with the name of their parked entry, held and problem nodes, the queued restores with the outcomes of those that ended **[changed]**, the entries a Publish answer to a first link released until the server applies their create (§2.7) **[changed]**, the nodes recorded as moved into an ignored folder that is no node, each with its file identity once another entry has taken its path, and which of them are folders the disk lost that L keeps only for the nodes recorded below them (§5.10) **[changed]**, and the engine's ID generator state. Connection state and queued outputs other than the in-flight commit and effect are not persisted. **[changed]** The effect in flight, the commit's `history_id`, the buffered result and the mass-delete state are new, and so are the commit layer's reverted nodes, waiting S updates, merged folders (A → B above), folders whose delete is split (§4.2) and the reduced op count after `LIMIT_EXCEEDED`. `koidrive_engine::state` holds the engine's part of this besides the nodes of R, L and S and the ID generator's state (`IdGen::state`), and restoring refuses a state that breaks an invariant. The engine does not implement the guard of §6.1 yet, so it holds no mass-delete state. Every question (the guard's, an ambiguous disappearance of §5.10, recovery's) is persisted with what it holds, so after a restart the engine emits `AskUser` again for each unanswered one; the driver shows a question ID once, so a repeat after a crash is harmless.

After a crash the engine restarts from that state. The fs driver first recovers the effect in flight from its record (§5.3), which leaves the disk in a state the record explains, and reports the outcome; only then does it rescan the whole root. Recovery makes adoption by guessing unnecessary for the engine's own effects. Adoption remains for one case: a device with no store at all (a first link, or a store that was lost), where the disk holds results of effects nobody remembers. The engine then **adopts** an unknown entry instead of uploading it as new when R has a node expected at that path with the same kind and content. Everything else on disk that L does not know is a new local node.

**[changed]** A store restored from an older backup, or copied to a second machine, is worse than a lost one, because it looks valid (review R3-1). It is detected through a per-device commit counter, `device_seq`. **[changed]** Its lifecycle (review R4-1):

- The store keeps the **accepted counter** *a*: the `device_seq` of the last commit whose result this device applied. A new commit takes slot *a* + 1, which is persisted with the commit before it is sent.
- A commit whose outcome is uncertain keeps its slot and its `commit_id` on every retry.
- A commit the server refused as a whole (a call-level error such as `MISSING_CHUNKS` or `UNSUPPORTED_VERSION`, so nothing was applied) does not use up its slot: the server advances its counter only when it accepts a commit. The re-planned commit gets a new `commit_id` and the same slot *a* + 1.
- Applying a commit's result sets *a* to its slot, in the same transaction that clears the commit in flight.

The server keeps, per device, the highest `device_seq` it accepted and that commit's result, updated atomically with accepting the commit, and reports the counter in `Welcome` as *w*. On reconnect:

| *w* against the store | Meaning | Action |
|---|---|---|
| *w* = *a* | the commit in flight, if any, was not accepted | resend it unchanged (table below). **[changed]** If its result has already arrived, the server accepted it and lost it, so this is the *w* < *a* row |
| *w* = *a* + 1, and the commit in flight has slot *a* + 1 | the commit was accepted and its response was lost | resend it unchanged: the server returns its stored result, which is applied as usual. Only if the server does not know that `commit_id` (`STALE_DEVICE_STATE`) is this a rollback |
| *w* = *a* + 1 with no commit in flight, or *w* > *a* + 1 | the store is behind the server: it was restored from a backup or copied | nothing is planned from this store; the space enters recovery (§6.4) with the store as evidence |
| **[changed]** *w* < *a*, or *w* = *a* with the result of the commit in flight held | the server lost commits of this device that it had accepted: its counter only grows and the store learns a slot only from its result | *a* := *w*; the commit in flight is dropped and its restores stay queued; R is recorded as ahead of the server and bootstrapped as for `AHEAD_OF_SERVER` (§4.4), which sends again what was lost |

A healthy store never shows the third row, because the commit is persisted before it is sent and *a* moves in the same transaction that clears it. **[changed]** The other recovery triggers are checked first: the root marker's counter (below) when the task starts, and the history before the counter. The driver takes a `Welcome` before the result of any commit the session answered after it, so *w* is never older than a commit the store acknowledged. A new connection also drops the results the session held behind a gap on the old one, so no event after a `Welcome` comes from an earlier connection, and a bootstrap after *w* < *a* takes nothing the server lost. A listing still out when such a `Welcome` arrives may have read the server before it, so its pages are dropped and the tree is listed again.

**[changed]** The counter covers only this device's own commits. A store restored to a point before it applied a remote change, with no commit of its own since, still shows *w* = *a*, yet the disk holds effects the store does not remember: a remote rename of n from /a to /b that reached the disk would rescan as a local delete of /a and a new file at /b (review of #7, CodeRabbit). So the store also keeps an **effect counter** *e*, the number of disk effects it has acknowledged, and the driver keeps a copy, *m*, in the root marker `.koidrive/space.json` (§6.2). The effect is recorded in the store first (§5.2); before it touches the disk, the driver writes *e* + 1 to the marker and flushes it; the store transaction that clears the effect in flight, whether it is reported done or failed, sets *e* to that value. A healthy device therefore has *m* = *e*, or *m* = *e* + 1 while an effect is in flight. On startup, after recovering the effect in flight (§5.3) and before any rescan is planned from, the driver reports *m*:

- *m* above *e* plus the effect in flight (one if an effect is recorded, zero otherwise): the store is older than the disk. Nothing is planned from it and the space enters recovery (§6.4) with the store as evidence;
- *m* below *e*: the disk, or at least its marker, was restored from an older state. The space pauses with a problem (§6.2) instead of reading the older files as local edits.

The counter is local, so it needs no protocol change. Like the other store-rollback triggers, it is part of the draft of §6.4 and is verified by simulation.

The commit in flight is handled by the history and the device counter it was built with. **[changed]**

| Situation after reconnecting | Action |
|---|---|
| `Welcome.history_id` equals the commit's `history_id` | Resend unchanged; `commit_id` makes the server return the stored result if it was already applied (spec §8 step 4). With the history fence of §10, the server also refuses it if the history changed in between |
| the server does not know the commit, and its `device_seq` is the next one the server expects from this device (proposed in §10) | The commit was never applied, so the server applies it now like any new commit. Its `base_seq` may be old, which only makes more changes count as unseen (spec §6); nothing is re-planned |
| the server reports `STALE_DEVICE_STATE`: the commit's `device_seq` is at or below the last one it accepted from this device (proposed in §10) | This store is older than the device's history on the server: it was restored from a backup or cloned. The outcome of the commit cannot be known, so it is never resent or re-planned; the space enters recovery (§6.4) |
| the history changed | Never resend and never re-plan it automatically. Its ops are kept as recovery evidence and the space enters recovery (§6.4) |

The crash cuts around a result: before the result's store transaction, the commit is still in flight and is resent, and the server returns the stored result, including any `MERGED_INTO` or `CONFLICT_COPY` re-keying, which is then applied once; after it, nothing is in flight. The simulation crashes devices at both cuts (§7.3).

**[changed]** A restore follows the same cuts, because a `Restore` op exists on the wire only inside the commit in flight. A request is durable once its own transaction commits, in an inbox table of the store that the driver's API writes and the task running the engine takes from. Taking it, queuing it in the engine and saving the engine state are one transaction. From there the restore stays queued through the build, the send and any resend, and it leaves the queue in the transaction that clears the commit and advances *a*. A commit that is abandoned because the server proved it was not applied only forgets the in-flight record, so its restores are sent again in the next commit, like its other changes. When the space enters recovery, the commit in flight and every queued restore are kept as they are, never resent and never planned again: they are the intents I₀ of §6.4.
