## Summary

- The engine keeps three trees keyed by `node_id`: the remote tree **R** (the server state this device has applied), the local tree **L** (the disk as last observed) and the synced tree **S** (the per-node merge base). A planner derives disk changes and commit ops from their differences, as in Dropbox's Nucleus ([Jayakar 2020](references.md#ref-nucleus), [Goldberg 2020](references.md#ref-trinity)). The only persisted intents are the one commit in flight and the one disk effect in flight, each recorded before it starts and bound to the server history it was planned against.
- The engine is a pure function of its inputs. It does no I/O, reads no clock and draws no randomness of its own; the file system, the network and the store are drivers around it.
- Correctness is stated in the vocabulary of Balasubramaniam and Pierce ([1998](references.md#ref-bp)) and Pierce and Vouillon ([2004](references.md#ref-unison)): the engine never overwrites a change it has not propagated, it only propagates user changes, and when activity stops every replica converges. Unlike Unison it does not stop at conflicts, because no person is watching; it keeps both sides instead, so the no-data-loss property is stated over file contents.
- The Space DO's commit order is the only order. Clients resolve conflicts they have already seen (a "rebase" of their local changes onto the newer remote tree) and the server resolves the ones they have not (spec §6.2). With a total order, moves need no CRDT: the server checks for cycles and the later move loses, which is the state-machine case of Kleppmann et al. ([2021](references.md#ref-move), §5.2).
- Disk changes never destroy bytes a user wrote, for regular file editing: programs that save by rename or open, write and close. The guarantee does not cover live databases or other long-lived writers that keep a descriptor open across a sync change (§5.2). A file the engine replaces or removes is first renamed into a quarantine directory, verified against what the engine expected, and only then moved to a local trash; a mismatch puts it back. A durable effect record names every path involved, so a crash at any point is recovered without deleting anything that might be a user's file.
- A mass-delete guard and a sync-root marker stop the two common ways a sync client destroys data at scale: a bug or a user mistake that deletes many files, and a missing or unmounted root that looks like "everything was deleted".
- After a rewind of the space on the server (`HISTORY_CHANGED`), or when this device's store turns out to be older than its history on the server, the engine runs a recovery (§6.4): it reconciles by node ID against the pre-reset trees, applies only what the device had not changed, and holds stale, local-only and changed files for the user's approval. This section is a draft: the simulation scenarios of §7.5 must verify it before 0.1.0, and that verification has not been done yet.
- Testing is a reference model plus deterministic simulation in the style of Trinity and FoundationDB ([Goldberg 2020](references.md#ref-trinity), [Apple](references.md#ref-fdb)): seeded, reproducible runs with crashes inside disk effects and store transactions, network faults, history resets and concurrent users, checked by an oracle that tracks the provenance of every write and every op. Native contract tests on real file systems cover what the simulation cannot.
- A small TLA+ model is worth writing for the commit and GC protocol (server side), not for the planner.
